Quick runs: how the agent behaves without memory

Branch quick/baseline-behaviour · gemma-4-31B-it on SGLang · temperature 1.0, thinking on · numbers read from each probe's summary.json

Short answer. Without memory, the agent mostly gives the same answer across runs. When it is wrong, it is usually wrong the same way every time. So a memory has to change the agent's choice; making runs agree would add little.

Why this matters for the memory question. We want to know if agents ignore memories. First we need to know what the agent does with no memory: where runs differ, and what they get wrong. That is the baseline any memory is compared against.

Terms used on this page

Run: one full attempt by the agent at a task. Each task was run 5 times.

Answer consistency: of all pairs of runs on a task, the share that gave the same final answer. 1.0 = all 5 agree.

Decision agreement: the same share, but for one decision the code actually made, such as the feature list or the model type.

Consistent failure: all 5 runs fail the same check, for example "never looked at the class balance".

Relative gap (DSBench modelling): how much of the distance from a simple baseline to a perfect score the run closes. 0 = baseline, 1 = perfect.

Contamination risk: how likely the model already knows the answer from training.

Asked each task's question without the data, 3 times. No agent runs.

Most "hits" are not memory of the dataset. Either the prompt names the study (BLADE), or the task wording or file name gives the pitfall away (for example, a file named "imbalance").

P9 · How much comes from the server alone?

Greedy decoding (temperature 0), so in theory every rerun is identical. 3 tasks, 4 reruns each.

There is no "same input, same output" on this server. Text differs early, then runs drift. 4 greedy runs of one BLADE task (crofoot) reached 3 different verdicts.

"Differs at" = the first message and character where a rerun's text departs from the first batched run.

P1 · Silent Failures and BLADE, no memory

15 tasks × 5 runs = 75 runs. Silent Failures (SF) tasks each hide a known problem in the data. BLADE tasks come with expert analyses.

Check explorer: which planted problems did the runs catch?

Each dot is one run. Green = passed the check, red = failed, grey = could not be judged.

The key finding. The agent writes the whole pipeline in 1–2 code cells and answers. It rarely looks at the data first. So nothing in its process would show it a 5% label, a "185cm" string or a column that leaks the answer.

Limits

  • 5 runs per task, so effects smaller than 1 run in 5 cannot be seen.
  • SF checks are judged by the same model that ran the agent. Its 3 judging draws agreed on run-checks, but no second judge was used.
  • The server is not reproducible even at temperature 0 (P9).
  • Several tasks are high contamination risk (P10). DSBench recall was not tested.
