# P12 context saturation: is a memory store needed while everything still fits in context?

Written 2026-11-15, before any P12 run. Asked for by the author (2026-11-15). Design and predictions approved by
The author as written (2026-11-15).

## Idea to test

If a problem is simple, or described well enough, and everything the agent should know fits in the context
window without filling it, then putting that knowledge straight into the initial context may do as well as a
memory architecture (store, retrieve, inject). A memory store would then be needed only where the context
saturates. P12 measures where that point is.

What we know already:
- Runs are far from the window. Peak context per run (prompt + output) was median 2.6k tokens on Silent
  Failures, 6.3k on BLADE, 6.8k on DSBench analysis, 5.5k on DSBench modelling; the largest run was 23.8k. No run
  passed 32k of the 64k we served.
- A hand-written one-sentence hint at the start was followed in 40 of 40 runs (P2/P4). But that hint knew the
  answer. P12 uses knowledge the agent wrote itself.

## Knowledge source (not hand-written)

Lessons written by the agent from its own earlier runs, ReasoningBank-style:
1. For every P1 and P1b run of the test tasks, gemma-4-31B (thinking off, temperature 0) gets the run's
   decisions, code and final answer, plus the evaluator's outcome, and writes 1 to 3 lessons (title, when it
   applies, what to do). Outcome given: Silent Failures, the names and questions of failed checks; DSBench
   analysis, right or wrong (not the gold answer); DSBench modelling, the relative gap.
2. The same is done for every other P1/P1b run, which gives a pool of lessons from unrelated tasks (the
   distractors).
3. The lessons are written once and frozen before any test run. I read all lessons for the test tasks and report
   how many state the planted fix outright (that decides how "oracle" they are).

## Arms (same agent, sampling, step budget as P1)

| Arm | What the agent gets at the start of the prompt | Approx. initial context |
| --- | --- | --- |
| A0 none | Nothing (reuse P1/P1b runs) | task only |
| M memory | Top-3 lessons retrieved from the whole pool by BM25 on the task text | + about 0.5k |
| C1 context, own lessons | All lessons from this task's earlier runs, no retrieval | + about 1-2k |
| C2 context, 32k | C1's lessons placed in the middle of other tasks' lessons and earlier run transcripts, total about 32k | 32k |
| C3 context, 110k | Same, filled to about 110k (window 131k, leaves room for the run) | 110k |

C1 to C3 carry the same relevant lessons; only the amount of other material around them changes. M is a
minimal memory architecture: a store plus retrieval, delivering a small context.

## Tasks (10, all with a ground truth)

- Silent Failures where all no-hint runs failed (the knowledge should matter): TF01, TF02, TF03, TF05.
- Silent Failures that no-hint runs already pass (no-harm check): TF04 leak-free, TF06 leak-free.
- DSBench analysis questions where P1b runs split: 00000043/1 (1 of 5 right), 00000017/29 (3 of 5),
  00000029/1 (2 of 5; 3 runs hit the step limit).
- DSBench modelling with the largest score spread: playground-series-s3e12.

Runs: 4 new arms x 10 tasks x 5 = 200 runs, plus about 250 short lesson-writing calls. The server is restarted
with a 131k window (image default) and fewer parallel requests for C3.

## Measures

1. Outcome per arm vs A0: the targeted SF checks, DSBench accuracy, relative gap.
2. Uptake: does the run act on a relevant lesson (SF checks; for DSBench, read by hand).
3. Answer consistency per arm.
4. Cost: prompt tokens per run, minutes per run, context fill at the last step.
5. Harm: on TF04/TF06, any check that passed in A0 and fails in an arm.

## Expected direction

1. C1 >= M on the SF tasks with consistent failures: the own-task lessons in context fix at least as many checks
   as retrieved lessons. Retrieval sometimes returns another task's lesson.
2. C1 and C2 are about equal: at 32k (a quarter of the window) the relevant lessons are still used.
3. C3 is worse than C1 on at least 2 of the 4 failing SF tasks (fewer runs pass the targeted check), because the
   relevant lessons are buried in 110k tokens. This is the saturation effect, if there is one.
4. M stays at about the same outcome as C1 at a small fraction of the context.
5. DSBench analysis changes little in any arm (right/wrong feedback gives weak lessons).
6. No arm breaks TF04/TF06 (at most 1 failed check that passed in A0).
7. Cost: C3 runs take at least 3 times the minutes of C1 runs.

If 1, 2 and 4 hold and 3 fails, the idea holds on these tasks: while it fits, context does the job and memory
adds nothing. If 3 holds, the drop point shows where a memory architecture starts to pay.

## Limits stated in advance

- The lessons come from the same task's earlier runs with evaluator feedback, the best case for any memory.
- Filler is realistic (other lessons and transcripts) but not adversarial.
- One model, 5 runs per arm, 10 tasks. Context loads tested: about 2k, 32k, 110k.
